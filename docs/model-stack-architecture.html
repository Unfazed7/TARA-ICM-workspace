TARA Aegis local model strategy

Model stack for private TARA automation

A production design for routing each TARA capability to the right local or VPC-hosted model: vision extraction, forced tool-calling, retrieval, reranking, and future LoRA adaptation.

01

Tool calling is the main gate

A smart model is not enough. The main TARA agent must reliably return forced tool/function calls and exact item counts.
02

No full-project prompt stuffing

Each call should receive one scoped chain: asset to damage to threat to attack to impact to risk.
03

RAG before fine-tuning

Use approved examples and company memory first. Fine-tune only after we collect clean reviewer-approved data.

VPC/GPU provider selection

private inference
TARA Aegis should choose GPU infrastructure by workload tier, not by brand name alone. The pilot target is a private vLLM endpoint for Qwen3-32B-class tool calling, with enough headroom to add a vision model and RAG services without exposing customer TARA data to public model APIs.

GPU fit

48GB VRAM is the practical floor for the main Qwen3-32B route. Use 16-24GB for the vision agent and 80GB+ when quality, longer context, or concurrency matters.

Serving/runtime fit

Require Linux, Docker, CUDA, persistent storage, and vLLM or an OpenAI-compatible server so the existing TARA Aegis LLM gateway can point to a private endpoint.

Security fit

Default to private networking, SSH key auth, locked firewall rules, encrypted volumes, no public model endpoint, and API keys scoped to TARA Aegis services only.

Reliability fit

Use non-interruptible instances for demos and production. Prefer reserved capacity or enterprise support once customer-sensitive assessments depend on the service.

Cost fit

Compare hourly GPU price plus storage, snapshots, idle volumes, bandwidth, and restart cost. Cheapest hourly GPU is not cheapest if it breaks long TARA runs.

Data posture

Customer TARA data should stay in our controlled deployment. Avoid shared community hosts for production unless isolation, logging, deletion, and support are verified.
Balanced pilot

RunPod Secure Cloud, 48GB GPU class

Best first choice for TARA Aegis pilot work: fast setup, clear GPU menu, Secure Cloud option, and 48GB cards such as RTX 6000 Ada, L40S, A40, or RTX A6000 for Qwen3-32B-class testing.
Enterprise ready

Lambda Cloud, A6000/A100/H100 class

Better when reliability, vendor maturity, reserved capacity, and customer-facing posture matter more than lowest hourly cost. Use A6000 for 48GB tests and A100/H100 for heavier throughput.
Lowest-cost experiment

Vast.ai On-Demand or Reserved only

Useful for non-sensitive model experiments and quick benchmarks. Avoid interruptible/community-style hosts for customer TARA data unless security and persistence are verified.

Decision rule

Scenario Choose
Experiment Vast.ai On-Demand or RunPod lower-cost 48GB class with synthetic/non-sensitive data only.
Pilot / customer demo RunPod Secure Cloud 48GB class first; move to 80GB if Qwen3-32B latency or context is weak.
Production sensitive data Lambda Cloud or hyperscaler GPU VPC with reserved capacity, private endpoint, logging, and customer-approved region.
Fine-tuning Use a separate training instance or cluster. Keep inference endpoint stable and do not fine-tune on production traffic directly.
Rule of thumb Never expose the vLLM endpoint publicly. Put it behind TARA Aegis backend/auth and allowlist only internal services.
!

VPC caution

Interruptible or community GPU hosts are useful for low-cost experiments, but they should not process customer-sensitive TARA assessments. For production, require non-interruptible capacity, private networking, encrypted persistent storage, and an explicit data deletion and logging posture.

Operating principle

TARA Aegis should not depend on model memory across calls. Every stage receives explicit JSON from previous stages. If a prompt exceeds context, the fix is chunking and scoped retrieval, not asking a larger model to remember everything.
