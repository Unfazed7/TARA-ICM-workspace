The Challenge

What we need to solve before we can sell this

TARA Aegis is a pipeline — a set of AI agents that run a full security assessment automatically. Before we can sell it to companies, we need to answer four questions.

IP Protection

If a company gets access to our files, they can copy the whole pipeline and run it themselves for free.

Data Isolation

Company A's security assessments must never be visible to Company B. Each customer needs their own private space.

Data Sovereignty

Automotive companies (OEMs, Tier-1 suppliers) will not send their vehicle security data to a third-party cloud server.

Organizational Memory

Each company needs the tool to learn from their past assessments — getting smarter about their specific systems over time.

The Solution

Self-hosted AI, deployed inside the customer's own infrastructure

Instead of asking companies to send their data to us, we send the entire product to them — packaged as a sealed, deployable unit. They run it on their own servers. Their data never leaves their building.

The core idea in one sentence

We package our pipeline into a sealed box, identify the best open-source AI models from Hugging Face for each task, and deploy everything inside the customer's private cloud — so they get the full product without ever seeing how it's built or having their data leave their network.

1

We package the pipeline

Our agents, prompts, and logic are sealed inside containers — runnable but not readable.

2

Models download to their server

Best-fit open source models pull from Hugging Face once during setup, then run offline forever.

3

Everything runs on their hardware

The pipeline calls their local model server. No external API. No data leaves their VPC.

AI Model Strategy

One model per task — best open-source fit from Hugging Face

Different stages of our pipeline require different capabilities. Rather than using one expensive model for everything, we identify the best free open-source model for each task — downloaded once, runs offline.

Stage 01 Reading and normalising the customer's asset list Lightweight fast model
Stage 02–03 Writing damage scenarios and identifying threats Qwen 2.5 72B
Stage 04 Modelling attack paths — the most reasoning-heavy task DeepSeek R1 70B
Stage 05–07 Impact rating and risk treatment decisions Llama 3.3 70B

Model choices are not fixed — we benchmark each one against our pipeline's output quality and swap as better models become available. The customer never needs to know which model is running.

Organizational Memory

Each company's system gets smarter with every assessment

Over time, the pipeline builds a picture of each company's systems — their common assets, recurring risks, existing controls, and past decisions. This gets injected automatically into every new assessment, making results more relevant and reducing repetitive input.

Company A — OEM

14 past assessments on OTA systems
Known assets: firmware server, diagnostic API, token vault
Preferred controls: SC-14, SC-22, ISO 27001 Annex A
Risk tolerance: Low — safety-critical systems

Company B — Diagnostics SaaS

6 past assessments on web portals
Known assets: session manager, audit log, dealer API
Preferred controls: NIST 800-53, OWASP Top 10
Risk tolerance: Medium — no direct vehicle control
✅  Because each company runs their own installation, their organizational memory is stored entirely on their own servers. Company A cannot see Company B's data — not by policy, but by physical separation.

Roadmap

What we build next to make this possible

Proposed next steps

1
Benchmark open-source models

Test Qwen 2.5, Llama 3.3, and DeepSeek R1 against each pipeline stage. Confirm tool-use reliability before committing to a model per stage.

2
Add per-stage model configuration

Update the pipeline so each stage can use a different model, configured via environment variables — no code changes needed to swap models later.

3
Build the deployment package

Package the entire stack (frontend, backend, pipeline, model server) into a single deployable unit. One command to install, one command to update.

4
Design the organizational brain

Define what gets stored after each assessment (asset patterns, recurring threats, accepted controls) and how it gets injected into the next run.

5
Add license management

Build the licensing server and the daily check inside the deployment. This gives us commercial control regardless of where the product is running.
